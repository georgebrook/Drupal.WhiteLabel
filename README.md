## Theming

The front end lives in `docroot/themes/custom/white_label` and follows **atomic design**, implemented on top of Drupal core's **Single Directory Components (SDC)**.

### Atomic design approach

Components are organised by complexity, under `components/`:

```
components/
├── quarks/       # Global, non-component styles: reset, grid, theme variables
├── atoms/        # Smallest reusable elements — heading, text, image, icon
├── molecules/    # Groups of atoms — button (icon + text)
├── organisms/    # Complex, composed sections — hero-image (image + content + button)
└── templates/    # Page-level layout components
```

The rule for where a new component belongs is simple:

- **Can it be broken down into smaller components and still make sense on its own?** If yes, it's a **molecule** (a small handful of atoms) or an **organism** (a composition of atoms/molecules into a distinct section of a page).
- **Can it not be broken down any further?** Then it's an **atom** — the smallest thing that renders on its own (a heading, an image, an icon, a single line of text).

Each level is only allowed to depend on levels at or below its own complexity — an atom shouldn't reach for another atom's internals, but an organism can freely compose molecules and atoms.

### SDC (Single Directory Components)

Every component is an SDC: a self-contained folder registered automatically by Drupal core, no manual library wiring required for its own assets.

```
components/[type]/[component-name]/
├── [component-name].component.yml   # Schema: props, slots
├── [component-name].twig            # Markup
├── src/
│   ├── [component-name].js          # Source JS — edit this
│   └── [component-name].scss        # Source SCSS — edit this
├── [component-name].js               # Compiled — auto-generated, do not edit
└── [component-name].css              # Compiled — auto-generated, do not edit
```

Only ever edit files under `src/`; the `.js`/`.css` next to them are build output.

**Using a component from a Drupal template, or from another component**, include it by its SDC namespace (`white_label:component-name`) and pass its declared props:

```twig
{% include 'white_label:button' with {
  button_content: 'Read more'|t,
  button_url: node.url,
  button_icon: 'chevron-down',
} %}
```

This is exactly how larger components are built out of smaller ones — for example the `hero-image` organism includes the `image` atom and the `button` molecule internally, rather than duplicating their markup:

```twig
{% include 'white_label:image' with {
  image_src: hero_image_src,
  image_alt: hero_image_alt,
  image_base_class: hero_base_class,
  image_blockname: 'image',
} %}
```

### BEM via `bem()`

Class names follow BEM (Block\_\_Element--Modifier), generated by a Twig function, `bem()`, provided by the `twig_bem` custom module (`docroot/modules/custom/twig_bem`) rather than written out by hand in markup.

```
bem(base_class, modifiers = [], blockname = '', extra_classes = [])
```

- With no `blockname`, it produces a **block**: `base_class`, plus `base_class--modifier` for each modifier.
- With a `blockname`, it produces an **element** scoped to that block: `blockname__base_class`, plus `blockname__base_class--modifier` for each modifier.
- `extra_classes` are appended as-is (for utility classes, JS hooks, etc.).

```twig
{# On the hero organism's own root: a block #}
<section class={{ bem(hero_base_class, hero_modifiers) }}>

{# On a child inside it, scoped as an element of the hero block #}
<div class="{{ bem('content', [], hero_base_class) }}">
```

When a component includes another (as above), pass the parent's block name down as the child's `blockname` so the child renders as `parent__child` rather than as its own independent block — that's what keeps nested markup readable as one BEM tree instead of colliding class names.

### DDEV theme commands

Front-end tooling (Vite build, SCSS, ESLint/Stylelint, SVG sprite generation) runs via npm inside the theme folder. The `ddev theme` command wraps `npm run` so it can be invoked from the project root, inside the web container:

```bash
ddev theme white_label start        # build once, then watch components/**/src and images/icons for changes
ddev theme white_label build        # one-off build with source maps
ddev theme white_label build:prod   # one-off build without source maps — run before committing
ddev theme white_label lint         # lint JS + SCSS
ddev theme white_label lint:fix     # lint and auto-fix
ddev theme white_label format       # Prettier, write
ddev theme white_label format:check # Prettier, check only
```

`ddev theme [THEME_NAME] [NPM_COMMAND]` runs `npm run [NPM_COMMAND]` inside `docroot/themes/custom/[THEME_NAME]`, so it works for any custom theme in the project, not just `white_label`.

Compiled CSS/JS and the generated icon sprite are committed to the repo, so `ddev theme white_label build:prod` (and a commit of the result) is required whenever anything under `src/` or `images/icons/` changes — there's no build step in CI.

See `docroot/themes/custom/white_label/README.md` for the full theme-level documentation (project structure, adding components/icons/third-party libraries, browser support).
